# 8. Метрики с нуля

Этот раздел можно читать отдельно от проекта. Он объясняет, что означают
числа в таблицах и почему нельзя сравнивать метрики разных задач.

## 8.1. Задача извлечения концептов

У нас есть абстракт статьи. Есть **gold** — эталонный список концептов,
размеченный людьми. Есть **prediction** — список, который вернула система.

Нужно ответить на два вопроса:

1. Насколько найденное правильное? — **precision**.
2. Насколько полно найдено эталонное? — **recall**.

## 8.2. TP, FP, FN и TN

Для каждого концепта есть четыре возможности:

|  | Система сказала «есть» | Система сказала «нет» |
| --- | --- | --- |
| В gold есть | TP (true positive) | FN (false negative) |
| В gold нет | FP (false positive) | TN (true negative) |

В извлечении концептов TN почти не используется: пространство всех возможных
концептов огромно, и «правильно не назвать» бессмысленно считать. Поэтому
оперируют TP, FP, FN.

## 8.3. Precision

```text
Precision = TP / (TP + FP)
```

«Из всего, что система назвала, какая доля действительно правильная».

Пример: система вернула 8 концептов, 5 из них есть в gold.

```text
Precision = 5 / 8 = 0.625
```

Precision падает, когда система добавляет лишние, «шумные» концепты.

## 8.4. Recall

```text
Recall = TP / (TP + FN)
```

«Из всего, что было в gold, какую долю система нашла».

В gold 10 концептов, найдено 5.

```text
Recall = 5 / 10 = 0.5
```

Recall падает, когда система пропускает концепты. В нашей задаче recall часто
ниже precision, потому что модель возвращает 6–8 концептов, а gold содержит в
среднем 12.6.

## 8.5. F1

```text
F1 = 2 * Precision * Recall / (Precision + Recall)
```

F1 — гармоническое среднее. Оно сильнее наказывает за дисбаланс: если
precision 1.0, а recall 0.1, F1 будет низким.

Пример:

```text
P = 0.625, R = 0.5
F1 = 2 * 0.625 * 0.5 / (0.625 + 0.5) = 0.625 / 1.125 = 0.556
```

F1 удобен, когда нужно одно число, но он скрывает, что именно происходит:
система может быть очень точной, но находить мало, или наоборот.

## 8.6. Почему не accuracy

Accuracy = (TP + TN) / все. В извлечении концептов TN огромно и не имеет
смысла: «правильно не назвать случайное слово» — не полезная работа. Поэтому
accuracy здесь не используют.

## 8.7. Exact и relaxed

**Exact** — строки должны совпасть после нормализации:

- lowercase;
- единственное число;
- без пунктуации;
- без артиклей.

Пример:

```text
gold:       "word sense disambiguation (WSD) systems"
prediction: "word sense disambiguation"
exact:      нет (строки разные)
relaxed:    да (Jaccard ≥ 0.5)
```

**Relaxed** — token Jaccard:

```text
Jaccard = |пересечение токенов| / |объединение токенов|
```

Если Jaccard ≥ 0.5, считаем совпадением. Это допускает сокращения и
модификаторы, но может склеить близкие, но разные концепты.

В отчёте exact всегда ниже relaxed, потому что каноникализация меняет строки.
Exact — нижняя граница, relaxed — более честная оценка смысла.

## 8.8. Micro и macro

**Micro** — складываем TP/FP/FN по всем примерам и считаем P/R/F1 один раз.
Доминируют большие статьи.

**Macro** — считаем P/R/F1 для каждой статьи, затем усредняем. Все статьи
равны, даже маленькие.

В нашем бенчмарке используется micro. Это стандартно для extraction, но
нужно указывать явно: micro и macro могут дать разные числа.

Пример:

| Статья | TP | FP | FN |
| --- | ---: | ---: | ---: |
| A | 5 | 3 | 5 |
| B | 1 | 1 | 9 |

Micro:

```text
TP=6, FP=4, FN=14
P = 6/10 = 0.6
R = 6/20 = 0.3
F1 = 0.4
```

Macro:

```text
A: P=0.625, R=0.5, F1=0.556
B: P=0.5, R=0.1, F1=0.167
macro F1 = (0.556 + 0.167)/2 = 0.361
```

Числа отличаются. Поэтому в отчёте важно писать, какой режим используется.

## 8.9. Content-only

Generic-сущности (`system`, `method`, `approach`, `algorithm`) часто являются
шумом. Content-only исключает их из gold и считает метрику по содержательным
концептам. Это не «улучшение модели», а другой срез оценки.

Если модель предсказывает generic-слова, в content-only они становятся FP и
снижают precision. Поэтому content-only дисциплинирует.

## 8.10. MRR

MRR (Mean Reciprocal Rank) используется в задачах ранжирования: для каждого
запроса правильный ответ имеет ранг; берём `1/rank` и усредняем.

Пример: правильный ответ на позициях 1, 2, 4.

```text
MRR = (1/1 + 1/2 + 1/4) / 3
    = (1 + 0.5 + 0.25) / 3
    = 0.583
```

MRR хорош, когда важен первый правильный ответ. Он сильно вознаграждает ранг
1 и почти не чувствует разницу между 100 и 101.

## 8.11. Hits@k

Hits@k — доля запросов, где правильный ответ попал в top-k.

```text
Hits@10 = число запросов с rank ≤ 10 / все запросы
```

Пример: 100 запросов, в 60 правильный ответ в top-10 → Hits@10 = 0.6.

Hits@k не учитывает, на каком именно месте внутри top-k; для этого есть MRR и
nDCG.

## 8.12. nDCG

nDCG учитывает и порядок, и градацию релевантности.

```text
DCG@k = Σ (2^rel_i - 1) / log2(i + 1)
nDCG@k = DCG@k / IDCG@k
```

`IDCG` — DCG идеального порядка. nDCG ∈ [0,1].

Пример: релевантности [3, 2, 0, 1].

```text
DCG = (2^3-1)/log2(2) + (2^2-1)/log2(3) + 0 + (2^1-1)/log2(5)
    = 7/1 + 3/1.585 + 1/2.322
    ≈ 7 + 1.893 + 0.431 = 9.324
```

Идеальный порядок [3,2,1,0] даст IDCG; nDCG = DCG/IDCG.

## 8.13. MAP

Average Precision (AP) — площадь под precision-recall кривой для одного
запроса. MAP — среднее AP по запросам. Используется в retrieval, когда важна
не только первая находка, но и весь список.

## 8.14. Triple F1

Для графа знаний важно не только найти узлы, но и правильно соединить их.

Предсказанная тройка `(h, r, t)` считается правильной, если после entity
linking и каноникализации она совпала с gold.

```text
Triple P = correct triples / predicted triples
Triple R = correct triples / gold triples
Triple F1 = 2PR / (P + R)
```

Это самая честная метрика «граф построен правильно», но она требует
размеченных отношений. В нашем бенчмарке её нет, потому что пайплайн не
предсказывает типы отношений SciERC.

## 8.15. Coverage, orphan rate, unresolved link rate

Для vault полезны инженерные метрики:

- **node coverage** — доля gold-концептов, попавших в граф;
- **edge coverage** — доля gold-связей;
- **orphan rate** — доля заметок без ссылок;
- **unresolved link rate** — доля `[[ссылок]]`, не находящих цель;
- **schema conformance** — доля заметок с правильным frontmatter;
- **graph density** — `2E / (N(N-1))` для неориентированного графа;
- **connected components** — число компонент связности.

Эти метрики не заменяют P/R/F1, но показывают, можно ли пользоваться базой.

## 8.16. Как читать таблицу LitGraphAgent

1. **Concepts exact** — нижняя граница; каноникализация мешает строгому
   совпадению.
2. **Concepts relaxed** — более честный сигнал смыслового совпадения.
3. **Content relaxed** — то же без Generic-шума; часто самый показательный
   столбец.
4. **Paper→concept edges** — бипартитная проекция тех же совпадений; не
   добавляет новой информации о качестве, но показывает, что граф строится.
5. **SOTA SciERC** — другая задача; не ставить в один ряд.

## 8.17. Частые ошибки

- Сравнивать exact F1 с relaxed F1 и делать вывод «модель стала хуже».
- Сравнивать concept F1 с SciERC entity F1.
- Считать relation F1, если типы отношений не предсказываются.
- Показывать лучший seed и молчать про остальные.
- Забывать про micro/macro.
- Оптимизировать метрику, а не качество графа: например, вернуть 100
  концептов, чтобы поднять recall, и разрушить precision.
- Считать 20 абстрактов «лидербордом».

## 8.18. Главное

Метрика — это линза, а не истина. Одно число не описывает систему. Поэтому в
проекте есть несколько сигналов: exact, relaxed, content-only, число
концептов, failures, время, QA, тесты. Только вместе они дают честную картину.
